ORAC GPU PORT: INITIAL SOURCE AUDIT
Date: 2 November 2026
Input: orac_test.tar.gz supplied by Piero Procacci

ASSESSMENT

The supplied source supports proceeding with a staged OpenMP target port.
The scientific algorithms and MPI ensemble structure can be preserved. The
principal work is reorganizing CPU-thread-dependent list storage, force
accumulation, and scratch memory; establishing persistent device data; and
porting integration/constraints and the full PME pipeline alongside forces.
Adding target directives to the existing force loops is unlikely to meet
the requested 7-10x whole-simulation acceleration.

This is a static source audit and analysis of supplied CPU reference logs,
not a successful rebuild, GPU implementation, or performance measurement.
No supplied source, inputs, or reference outputs were changed. A separate
copy of src was used for the build attempt.

SCOPE AND REPRODUCIBILITY

The archive contains 561 members (47,459,395 expanded bytes), including
395 Fortran source files with approximately 93,975 lines. These counts
include alternative/older implementations; they do not describe the active
GPU porting scope. Major execution paths and their dependencies were read;
this is not a line-by-line correctness review of every source file.

Four examples are present:
  test1: ordinary MD, eight OpenMP threads.
  test2: segment HREM, four MPI ranks with two threads each.
  test3: NE alchemy using force_alchemy.f (soft-core).
  test4: NE alchemy using force_alchemy_shifted.f (shifted potential).
Both alchemical tests use four ranks with two threads each.

The reference system contains 14,900 atoms: 1,715 solute atoms and 4,395
three-site water molecules. It has 5,082 atomic groups, or 2.93 atoms/group
for this example (distinct from the typical 3.4 discussed previously).
The force-field files, coordinate files, binary topology files, and HREM
restart files needed by the examples are present.

The actual test1/test2 MTS settings are:
  N0 0.375 fs; N1 0.750 fs; SR/M 1.500 fs;
  IR/L 3.000 fs; LR/H 15.000 fs.
  M/L/H radii: 5.1 / 7.8 / 10.0 Angstrom, with healing/buffer settings.
  PME: alpha 0.37 Angstrom^-1, order 4, grid 48 x 48 x 48.
  Reciprocal space belongs to IR/L, not LR/H.
test3/test4 use radii 5.0 / 8.1 / 12.5 Angstrom and grid 48 x 49 x 48.
These input values, switching widths, and scheduling must be preserved;
the earlier [0,5], [5,7], [7,cutoff] discussion was schematic.
All four examples use thermostat/barostat control; test1 is not an NVE
validation case even though it records an energy-conservation diagnostic.

BUILD CHECK

In a separate source copy, ran:
  bash ./configure -GNU -FFTW -OMP
  make
Configuration generated the expected GNU-FFTW-OMP target. It also emitted
'gfortran: command not found'. make stopped at the first compilation,
because gfortran is absent. MPI wrappers/launcher and Intel/PGI compilers
are also absent. FFTW runtime libraries exist, but its development package
and fftw3.f03 were not found. No NVIDIA GPU utility was found; GPU hardware
and working offload support have not been established.

A standard package-index update could not run in the environment, so the
missing toolchain could not be installed by that route. This is an
environment limitation, not evidence of a compilation defect in ORAC.

Build observations from the actual configuration:
  * configure selects ifort/mpiifort and pgfortran, not ifx/nvfortran by name.
    Modern compiler commands should be selectable without hardcoding them.
  * The supplied GNU configuration has -fallow-argument-mismatch. No
    -std=legacy flag is added by the inspected GNU branch. Whether it is
    necessary with a particular compiler remains untested.
  * The linked threaded FFTW backend is -lfftw3_threads (pthreads), not
    -lfftw3_omp. ORAC's surrounding PME loops use OpenMP.
  * README executable paths use ../../src from test directories; relative
    to the supplied tree the executable is ../src/GNU-FFTW-OMP/orac or
    ../src/GNU-FFTW-OMP-MPI/orac. Paths inside MPI-generated TST directories
    intentionally use ../../ff and must not be shortened indiscriminately.
  * Serial MD writes topology files referenced by NE tests. Run test1 first,
    or explicitly select the matching supplied binary topology. Preserve
    the supplied HREM restart set separately when rerunning test2.
  * CPU model, compiler versions, FFTW version, and rank/thread affinity
    were not found in the README files. They are needed for comparisons
    against the supplied machine; they do not block static analysis.

TIMING CAVEAT CONFIRMED IN SOURCE

src/lc_list.f:89 starts a timer, and :232-234 adds the elapsed interval to
time_u. src/mtsmd.f:2419-2436 also times the lc_index/lc_list block and adds
that enclosing interval to the SAME time_u. Thus lc_list wall time is
counted twice during the timed MD-loop update path. The CPU counter is
not updated at the enclosing site, explaining why the update wall/CPU
columns are especially hard to compare.

Task timers also run during initialization before the final MD-loop timer
baseline (mtsmd.f:2377-2378). Therefore sums of reported task counters are
not a clean exclusive partition of the final total. In particular, the NE
task sums exceed their total times by approximately 2.5 s. Correct the
timer scope before drawing precise Amdahl limits or attributing those
differences wholly to one cause. GPU timing must account for completion
of asynchronous work rather than measuring only kernel launch time.

The robust qualitative conclusion is that IR and SR dominate real-space
force cost; integration and constraints are material, particularly test1.
On test1 the three direct-space counters total 25.9412 s, versus 16.1691 s
for integration plus constraints. A rough model based on these counters
would cap a direct-force-only port near 1.8x, and a port leaving integration
and constraints unchanged near 3.6x even if all other tasks became free.
These are illustrative ceilings, not calibrated predictions, because of
the timer issues above. A 7-10x complete-run goal requires wider coverage.

SOURCE FINDINGS AND PORTING CONSEQUENCES

1. Preserve the mathematical MTS hierarchy; replace thread-specific storage.

src/mts_forces.f:56-95 selects u/h/l/m cutoff and buffer parameters;
:121-155 dispatches standard, HREM-segment, soft-core, and shifted forces.
src/mtsmd.f:1986-2027 initializes forces in H -> L -> M order, passing
nnlpp0 -> nnlpp -> nnlpp1. The loop refreshes the hierarchy at its existing
frequencies, including list-only calls. This is a useful dispatch boundary.

However, nnlpp and mapnl are packed by CPU thread, and force.f:228-245
uses OMP_GET_THREAD_NUM plus array_omp ownership masks. Each thread scans
the outer group loop and selects its groups; variable-length lists are
traversed using running cursors. These assumptions cannot simply become
GPU thread identities.

Proposed representation: group-indexed offsets/counts and contiguous
neighbor identifiers for each level, independent of CPU thread count.
Construct/filter lists in the existing LR -> IR -> SR sequence. Use
count/scan/fill or bounded per-group capacity with explicit overflow
handling; benchmark whether filtering and force evaluation should share
a kernel or be separate launches. Their logical association is preserved
either way. Keep the lists on-device across MTS calls.

2. Group switching is more than multiplying pair forces by a switch.

src/force.f:262-340 uses group distances for shell classification, inner
list filtering, and switching. :751-840 forms S'V from cmap2 and dswrs,
then distributes it by gmass across group atoms, including virial terms.
Replacing group cutoffs with atom cutoffs would change the algorithm.

The proposed compute-then-subtract exclusions can be explored, but the
correction must remove both switched pair contributions and their S'V
group contributions, plus energy, virial, segment-energy, and NE work
terms. Existing same-group treatment and separate 1-4 routines must be
preserved. A naïve subtraction of the unswitched excluded pair force is
insufficient. Avoid evaluating a self interaction and test cancellation
at short excluded-pair distances before any precision reduction.

3. Force scratch and reductions need a GPU-specific execution layout.

src/force.f:85-90 defines three whole-atom temporary force arrays and
:193-194 reduces them across threads. :113-121 declares large map arrays;
the OpenMP region makes the masks and work arrays private (:203-209).
The supplied parameters set m1=130000, ngrpmax=1572, natmax=6288. At those
capacities, private masks and work arrays are unsuitable per GPU lane.
Ordinary/HREM and alchemical paths have related but distinct scratch layouts.

Preserve the useful existing separate x/y/z arrays. Replace global-size
per-thread scratch with compact pair/group work, team-sized bounded
buffers, and explicit accumulation. Benchmark atomics against per-team
partial results or gather-based accumulation; a full list computing pairs
twice is another option, with energy/virial accounting checked carefully.
No winning method can be selected from static inspection alone.

4. The outer linked-cell construction has a serial component.

src/lc_list.f:89-112 builds headp/chainp in a serial loop; its apparent
parallel directives begin !!$OMP and are comments. Simply enabling them
would race on the head pointers. Subsequent traversal is pointer chasing
through linked cells and CPU-thread-owned output lists (:120 onward).

Replace linked chains with compact cell occupancy: bin group centers,
count/scan/scatter group identifiers, and traverse contiguous cell ranges.
Retain groups, the current periodic metric, neighbor radius/healing/buffer
semantics, and pressure-dependent stencil updates. Start by comparing
exact group-pair sets on fixed snapshots. The spherical implementation
can remain a reference/fallback. Do not introduce extra group-extent
padding or an atomwise cutoff unless a separate algorithm change is agreed.

5. Neighbor capacity should follow actual workload rather than maxima.

src/mtsmd.f:629-633 allocates four arrays, each approximately mpp integers,
where mpp=524*50000=26,200,000 with the supplied config.H. Assuming the
usual four-byte default integer, these four arrays reserve approximately
419.2 MB (400 MiB) per MPI simulation before other data. The fourth is a
candidate-list array used by the spherical route; linked-cell operation
does not need a full-size equivalent on the GPU. This is allocated
capacity, not a measured resident-memory footprint or actual list length.
Compact, independently sized lists would reduce device-memory pressure,
especially if several simulations eventually share a GPU.

6. PME has a clear backend boundary, but the full pipeline needs attention.

src/pme_fftw3.f90:109-118 allocates Q/FQ, computes charge assignment,
performs forward FFT, scalar sum, inverse FFT, force interpolation, then
deallocates Q/FQ on EVERY reciprocal call. do_pmesh_alchemy.f90:65-88
similarly allocates four grids/buffers, performs TWO forward transforms
and one inverse, and computes finite work as eer-eer0 at fixed coordinates.

First introduce persistent per-simulation PME workspace and a plan/context
type. fftw3_pme_init.f90:44-56 currently makes plans with FFTW_ESTIMATE
and nthr2 threads using temporary arrays, then deallocates those arrays.
Check new-array alignment compatibility when reusing plans; persistent
aligned buffers simplify that requirement. Plans are already created at
initialization, not on every step. No explicit fftw_destroy_plan call was
found by searching the Fortran sources.

spme.f90 stores plans as INTEGER*8, whereas initialization uses C_PTR.
do_pmesh_alchemy uses legacy dfftw_execute calls; the ordinary path uses
the ISO-C-bound fftw_execute interface. Standardize opaque handle typing
and interfaces rather than propagating these ABI assumptions into cuFFT.

fill_charge_grid in pme_fftw3.f90:265-269 uses a full Q-array reduction;
alchemy_charge_grid.f90:62-72 reduces both Q and Q0. These should not be
transplanted directly to massive GPU parallelism. Evaluate atomic charge
deposition or tiled/bin-based deposition, with local reductions where
useful. Gradients are naturally parallel over particles; scalar sums over
mesh points need controlled reductions for energy and virial.

Keep FFTW for CPU, provide optional cuFFT on NVIDIA, and isolate both
behind initialize/execute/destroy operations. The GPU path must keep the
mesh on-device through deposition -> FFT -> scalar sum -> inverse ->
interpolation. Backend interoperability must check device/context and
ordering between OpenMP kernels and library transforms. No custom CUDA
force kernels are required by this architecture.

The timer recpr F covers the reciprocal-space routine and corrections,
not FFT execution alone. Its value cannot quantify FFTW inefficiency.
Instrument PME sub-stages before choosing FFTW planning/thread changes.
Keep IR scheduling and existing self/exclusion/1-4 correction allocation.

7. Constraints already contain multiple solution paths.

src/rattle_verlet.f and rattle_correc.f partition connected constraint
components using cnst_protl and CPU-thread masks. They contain iterative
branches and small-matrix solution paths with nmat=20; this is not just
one global serial SHAKE loop. Setup loops also traverse atoms/constraints.

Port work by independent constraint component. Consider a specialized
analytic rigid three-site-water solver, preserving position AND velocity
constraints, and a separate general solute solver. Small component solvers
can be retained/adapted initially. Replacing every constraint with one
method is unnecessary. Validate within the existing molecule-frame,
thermostat/barostat, and nested MTS update sequence, including virials and
tolerances; do not assume standard Cartesian integration is equivalent.

8. MPI architecture is particularly favorable for the requested use case.

src/rem.f90:449-498 exchanges three energy components and scaling-label
indices; it updates rem_factor and gathers labels. Coordinates are not
exchanged in this path. Retain host MPI, copy the small energy data back
at exchange points, then update device scaling parameters. Whole particle
arrays need not cross host/device solely for this label exchange.
Map local MPI ranks to available devices explicitly. One simulation/GPU
is the first implementation target; do not build spatial multi-GPU domain
decomposition into the initial scope. Existing barriers may become more
visible after acceleration and should be timed before any redesign.

9. Preserve NE work semantics, not just energies and forces.

mts_furier_alchemy.f:94-124 constructs current and previous charge arrays.
do_pmesh_alchemy.f90:77-82 evaluates their reciprocal energies at the same
coordinates and takes the finite difference. Direct-space kernels also
use current/previous lambda variables. Preserve finite-increment work,
MTS update order, self/correction terms, and shifted versus soft-core
definitions. A generic derivative-only API is not an automatic substitute.
Forward/reverse work-distribution validation needs additional matched
cases beyond the two supplied removal examples.

RECOMMENDED IMPLEMENTATION ORDER AND ACCEPTANCE GATES

Stage 0 -- reproducible CPU baseline and exclusive timing.
  Supply/install GNU Fortran, FFTW development files and a matching MPI
  stack. Run in disposable directories. Fix README launch paths locally,
  preserve references/restarts, record compiler/library/hardware/affinity,
  and repair timer scopes. Run all four examples. Add deterministic
  fixed-snapshot comparisons of force, energy, virial, and NE work terms.

Stage 1 -- data and kernel prototype.
  Define runtime-sized per-simulation state and group-indexed list offsets;
  initially retain exclusion masks/logic as a correctness reference. Build
  a standard-force OpenMP target prototype with small bounded scratch.
  Compare each shell, switch-region group derivatives, and pair sets.
  Then compare alternate accumulation and exclusion-correction schemes.
  Explicitly verify target execution rather than silent CPU fallback.

Stage 2 -- device-resident MD path.
  Move the frequently used updates, group/COM coordinate transformations,
  bonded forces, and position/velocity constraints onto the device. Preserve
  every MTS force level, correction, and update frequency. Minimize host
  transfers across the 0.375 fs inner steps. Validate double precision
  first, including a dedicated NVE run and NVT/NPT statistical comparisons.

Stage 3 -- resident PME and FFT backends.
  Introduce persistent buffers, OpenMP deposition/scalar/interpolation,
  CPU FFTW and optional cuFFT interfaces, and explicit ordering. Test both
  supplied grids, especially 48 x 49 x 48, normalization, virial, and
  exclusions. Extend to two-charge-grid NE work without changing its
  finite-difference definition.

Stage 4 -- HREM and both NE variants; portability/performance qualification.
  Port segment-energy accounting and lambda/scaling updates, integrate
  host MPI exchange, and validate forward/reverse work and exchange data
  on fixed states. Retain existing scientific input syntax. Benchmark full
  simulations against the SAME CPU core allocation and physical settings,
  reporting ns/day, replica/switch throughput, and resource allocation.
  Qualify at least NVIDIA and AMD toolchains before claiming portability.

The entire programme is staged: early measurements should determine
whether atomics, duplicated pair evaluation, list fusion, or alternate
constraint solvers are worthwhile. No static result here establishes a
7-10x gain on any GPU, including GTX 1050 Ti, or a specific gap to GROMACS.
Hardware precision performance and compiler/device compatibility remain
benchmark questions. Broadly retaining double precision on a low-end GPU
may constrain speed; mixed precision is a later validation decision.

MATERIAL STILL NEEDED FOR EXECUTION/PERFORMANCE QUALIFICATION

No additional ORAC source archive is required to continue this audit.
For baseline reproduction/comparison: compiler and FFTW versions, CPU model,

Fortran/MPI build environment and target GPU access are needed to execute
